## 1. Objetivos del producto

### Objetivo principal

Construir un **SaaS B2B** de tipo ERP-lite llamado **Uyuni** que ofrece un **Core-CRM** genérico (clientes, agenda, caja básica) adaptable a múltiples nichos:

- Clínicas
- Ferreterías
- Organizaciones de gestión de personal y activos
- Otros nichos futuros

### 1.1. Objetivos funcionales (FO)

| ID | Objetivo | Medida de éxito |
|---|---|---|
| FO-1 | Autenticación robusta por email + password | 0 credenciales sin cifrar en storage; lockout tras 5 intentos |
| FO-2 | RBAC granular por módulo y acción (CRUD) | Permiso denegado con código HTTP específico |
| FO-3 | Multi-tenant con planes + cuotas | Imposible invitar a user 6 si el Plan es `max_usuarios=5` |
| FO-4 | Auditoría completa (access + CDC) | 100% de escrituras de dominio con `entity_id`, `tenant_id`, `old/new` |
| FO-5 | CRUD de activos/logística (heredado) | Assets, Areas, Groups, Statuses, Institutions, Acts |
| FO-6 | CRUD de organización (heredado) | OrgUnits, Positions, Staff |
| FO-7 | CRUD de tareas (heredado) | Tasks |
| FO-8 | ETL sincronización de fuente externa (heredado) | Sync equivalente a `sync_siger.py` (UPSERT + soft-delete) |
| FO-9 | Catálogos dinámicos optimizados (heredado) | `GET /catalogs/{name}` y `POST /catalogs/bulk` |
| FO-10 | Selector de tenant en el frontend | `GET /me/tenants` returns list of memberships |

## 2. Stack tecnológico ratificado

### 2.1. Por qué NestJS + TS (no FastAPI) — para proyecto desde cero

> El usuario confirmó que el núcleo de valor a 2-3 años es **CRUD + multi-tenant puro**
> y que "tal vez" se use IA. Ver `15-ADRs.md` ADR-001 para el análisis completo.

| Dimensión | Razón de la elección |
|---|---|
| Coherencia con Angular 21 | DTOs TS compartidos en monorepo Nx; un solo lenguaje |
| Multi-tenant idiomatic | Guards + Interceptors globales (AsyncLocalStorage) |
| CLI + scaffolding | `nest g resource` acelera CRUD |
| Equipo único TS | Contratar full-stack TS reduce fricción vs mixto Python/Angular |
| IA futura | Hedging: si aparece, micro-servicio FastAPI aislado vía HTTP interno |
| Patrimonio funcional | Auth, RBAC, audit, catalogs, módulos — todos portables a NestJS sin pérdida |

### 2.2. Stack

```
NestJS 11.x  +  TypeScript 5.x  +  Prisma 6.x  +  PostgreSQL 16+
Jest  +  supertest  +  Testcontainers
Pino (logger)  +  class-validator  +  class-transformer
@nestjs/jwt + passport-jwt  +  bcrypt
ESLint + Prettier  +  Husky
Nx monorepo: apps/api + apps/web + libs/shared
```

## 3. Glosario

| Término | Definición |
|---|---|
| **Tenant** | Cuenta empresa cliente. Inquilino. Aislado por `tenant_id` |
| **TenantUser** | Membresía de un `User` en un `Tenant` con un rol |
| **Plan** | Tier de suscripción: `max_usuarios`, `precio`, `name` |
| **User** | Persona física. Login global por `email` |
| **Role** | Rol asignado a un User dentro de un Tenant: `Admin`, `Empleado`, etc. |
| **Module** | Componente del sistema: `assets_assets`, `core_staff`, etc. |
| **RoleModule** | Permisos CRUD de un Role para un Module |
| **PermissionAction** | `CREATE`, `READ`, `UPDATE`, `DELETE` |
| **Scope** | Flujo de datos accesibles por un usuario en un tenant |
| **TenantScope** | `All` (todos los registros del tenant) o `Own` (solo los creados por el user) |
| **Audit log** | Registro de auditoría (Access o CDC) |
| **Access audit** | Log de petición HTTP (method, path, status) |
| **CDC** | Change Data Capture: log de cambios `old` vs `new` en entidades |
| **TenantContext** | DTO propagado en cada request vía DI: `{ tenant, user_id, role, scope }` |
| **TenantGuard** | Guard de NestJS que valida membresía y setea TenantContext |
| **TenantInterceptor** | Interceptor que injecta `tenant_id` en transacciones Prisma (RLS) |
| **Bulk catalogs** | `POST /catalogs/bulk` para resolver múltiples selectboxes en 1 req |
| **CatalogProvider** | Implementación concreta por slug (Strategy pattern) |
| **External ID** | ID secuencial de fuente externa (legacy DB), mapeado a UUID interno |
| **Soft-delete** | `is_active=false` en vez de borrado físico |
| **RLS** | Row-Level Security de PostgreSQL: `CREATE POLICY ... USING (tenant_id = current_setting('app.tenant_id'))` |
| **Quota** | Límite de un Plan; validado en invitación de usuarios |
| **JwtBlacklist** | Tabla `revoked_tokens` para logout y refresh rotation |

## 4. Personas de uso

| Persona | Permisos típicos | Tenant scope |
|---|---|---|
| **Platform Admin** | Superuser global; bypass RBAC; ve todos los tenants | `platform` |
| **Tenant Admin** | CRUD en su tenant; invita usuarios hasta `plan.max_usuarios` | `tenant:all` |
| **Empleado** | Read/Create limitado; no invita, no borra | `tenant:own` |
| **Auditor** | Read-only en audit + reportes | `tenant:read` |

## 5. Reglas de negocio invariantes

1. **Login por email**: nunca por `username`. `User.email` unique global.
2. **Un usuario pertenece a 0..N tenants** con un rol distinto por membresía.
3. **Cuota de Plan**: `count(tenant_users WHERE tenant_id=T AND is_active=true) <= plan.max_usuarios`. Exceder = `409 PLAN_QUOTA_EXCEEDED`.
4. **Aislamiento de datos**: ningún endpoint de dominio puede retornar datos de un tenant distinto al activo.
5. **Superuser bypass**: `User.is_superuser=true` puede omitir RBAC (no RLS — RLS siempre se aplica).
6. **Refresh token rotation**: cada `refresh` invalida el token anterior (blacklist).
7. **Lockout**: 5 intentos fallidos → lock 15 min (`SECURITY_LOGIN_MAX_ATTEMPTS`).
8. **Audit inmutable**: `audit_logs` y `audit_entities` son append-only; DELETE prohibido vía API.
9. **Soft-delete por defecto**: доменmains usan `is_active=false`; hard-delete reservado a admin script.
10. **Timezone UTC**: todos los timestamps DB en UTC; conversión a local solo en presentación frontend.

## 6. Principios de implementación

- **NestJS idiomatic**: un módulo por bounded context. `Module → Controller → Service → Repository/Prisma`.
- **Modularidad**: cada módulo export solo sus DTOs públicos; servicios internos `@Injectable()` sin exportar.
- **Prisma como detalle de infraestructura**: Services dependen de interfaces (`Port`) no de `PrismaClient`. Ver `02-ARCHITECTURE-SPEC.md`.
- **DTOs en `@saas/shared`**: frontend y backend consumen mismos tipos; cero drift contract.
- **Sin `any`**: ESLint prohibe `any`; `unknown` + type-guard cuando es inevitable.
- **Errores tipados**: clases `NotFoundException`, `BusinessException`, mapeadas en `ExceptionFilter` global.
- **Logging structured**: JSON con `requestId`, `tenantId`, `userId`, `path`, `durationMs`.
- **Tests de dominio aislados**: mocks de Prisma via `interface`; no dependen de Postgres real (excepto E2E).
